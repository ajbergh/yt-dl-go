# Production web UI: 1080p download checks — 2026-10-30

## Result

Four additional videos were submitted through the production web UI with **Up to 1080p** selected. Two downloads failed, one completed at actual 1080p, and one completed at 858p. The app therefore does **not** pass a general 1080p reliability check.

| Video | Source duration | Production UI result | Actual saved file |
| --- | --- | --- | --- |
| [Caminandes 2: Gran Dillama](https://www.youtube.com/watch?v=Z4C82eyhwgU) | 2:26 | Failed: “Job storage limit reached; remaining entries were not downloaded” | No finalized media |
| [Caminandes 3: Llamigos](https://www.youtube.com/watch?v=SkVqJ1SGeL0) | 2:30 | Completed; visible in Library | 1080p MP4, 40,041,072 bytes; both tracks verified |
| [Spring](https://www.youtube.com/watch?v=WhWc3b3KhnY) | 7:44 | Completed below the requested ceiling; not an exact-1080p pass | 858p MP4, 135,432,339 bytes; both tracks verified |
| [Big Buck Bunny 60fps](https://www.youtube.com/watch?v=aqz-KE-bpKQ) | 10:35 | Failed: “Job storage limit reached; remaining entries were not downloaded” | No finalized media |

Spring's 858p result is reported separately rather than counted as a failed download or a 1080p pass. Its initial strict-dimension assertion failed; an independent check of the saved file at its actual height subsequently passed.

## What was exercised

- Existing production executable: `dist/youtube-downloader.exe`, serving `http://127.0.0.1:8080/`. No fixture build, mock media service, or test-tagged backend was used.
- Branch revision: `9fc0c8d0e456885ac2a6459a7fc5c08d6470f221`.
- Executable SHA-256: `ac9e1581daa95aafdcc6fe920a2326f8d550f99d9f7b36c02c72085b75677714`.
- Real Chromium/Edge frontend: opened the production page, entered each watch URL, clicked **Inspect qualities**, selected **Up to 1080p**, confirmed download rights, and clicked **Add 1 to queue**.
- Observed the UI-generated POST requests to confirm `quality: "1080"` and the matching video URL. Downloads were not created by direct test API calls.
- Used the default automatic video strategy. Saved preferences were not changed, and 360p recovery remained disabled.
- Captured inspection, queue, completion/Library, and failure screenshots. Read-only API polling supplemented the UI observations to retain exact job state after terminal working-state eviction.
- Read successful published files through the existing `TestLivePublishedFile` check: actual container height, video/audio presence, packets through EOF, and both tracks reaching the inspected source duration within the existing three-second tolerance. This does not decode every frame.

Completed output files and failed job history remain in the app for inspection. The production service was left running. No application source code or download settings were modified during this test run.

## Remaining failure

Caminandes 2 failed at approximately 53.7 MB received; Big Buck Bunny failed at approximately 258.1 MB received. Both reported a storage-limit error despite the configured 10 GiB job cap. The exact cause of that limit error has not been established; these are failures, not passes obtained by retrying until success.

A separate diagnostic reproduction of Caminandes 2 at 1080p also failed. Its trace showed browser capture/preparation errors followed by repeated native HTTP 403 responses at byte offset 25,165,824. That diagnostic run was **not** submitted through the UI and is not included as another UI test case. It does not establish that the original storage-limit message has the same cause.
